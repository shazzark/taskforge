# Technical Requirements

## CLI contract
Loopback and approval-controlled public HTTPS browser audits are supported. Public journeys require exact owner approval and support visible-text checks, constrained same-origin GET search, classified read-only same-origin link navigation, opening a visible book-result link, and browser back. Every audit performs bounded page-load diagnostics with screenshots, capped DOM snapshots, console/network observations, and safe same-origin HEAD route probes. The unauthenticated browser blocks private/internal destinations, unapproved origins, WebSockets, state-changing request methods, and page-provided links whose destinations are not classified as read-only; link classification is conservative and does not certify server behavior. Requests, bytes, DOM work, screenshots, and runtime are bounded. Reports identify observed failures, hypotheses, and coverage limitations and are not comprehensive security/accessibility certifications. Live owner acceptance remains pending. `resume <run-id> --input <path>` accepts uncertain `csv-analyze` and `document-analyze` runs, reacquires exact-file approval, and checks the same input bytes and workflow hash before deterministic replay.

Implemented CLI commands include `taskforge run csv-analyze --input <path>`, `taskforge run document-analyze --input <path>`, `taskforge run pdf-report --input <report.json> --output <new.pdf>`, `taskforge run repo-inspect --root <directory>`, `taskforge run source-review --root <directory> --file <relative-path>`, `taskforge run model-investigate --root <directory> --file <relative-path> [...]`, `taskforge run github-issues --repository <owner/name>`, `taskforge run file-patch --root <directory> --target <relative-path> --content-file <relative-path>`, `taskforge run git-diff --root <directory>`, `taskforge run software-check --root <directory> --check <node-test|typescript-check>`, `taskforge tasks list`, `taskforge tasks inspect <task-id>`, `taskforge tasks validate <task-id> --inputs-json <object>`, `taskforge resume <run-id> --input <path>`, and `taskforge history list`. The built-in task registry validates declarative instructions, inputs/outputs, fixed tool-capability identifiers, examples and schema-level conformance cases; no task command executes these definitions or accepts user-installed definitions yet. CSV and document workflows read one explicitly approved file and store redacted metadata; PDF report output asks approval for the exact target and content hash, creates a new file only, and validates the written hash; document parsing supports TXT, Markdown, text PDF, DOCX, and XLSX and persists aggregate counts only. Resume revalidates input/workflow hashes. Repository inspection requires interactive exact-root approval, inventories bounded metadata only, skips links/secret paths/generated folders, and runs no commands. Source review requires exact root/file-set approval, accepts bounded UTF-8 source only, redacts common credential patterns locally, and sends/persists no source content; its redaction is heuristic. Model investigation displays up to five redacted source files, requests a separate provider-transfer confirmation, sends no tools, and stores neither excerpts nor findings. Public GitHub issue reading asks before one tokenless GET, returns at most 20 validated open issue titles, excludes pull requests, and persists nothing; private-repository access is not implemented. File patching binds replacement content and target snapshot into a preview, displays redacted before/after text, requires explicit approval, then writes through the revalidated open target handle. This preserves permissions and prevents a changed path from redirecting the write; in-place writes are not crash-atomic and cannot coordinate concurrent same-file writers. Git diff review requires approval of the exact canonical root and staged tracked file list, disables external diff/text conversion, caps output at 48 KiB, rejects secret paths, and displays heuristic-redacted source locally without persistence. It excludes unstaged and untracked files. Software checks require separate approval for the exact root and one fixed command; stdout/stderr are drained, bounded, not displayed, and not persisted. The command is not an OS sandbox; tests may run repository code. Natural-language goal dispatch and expanded history deletion remain planned. `chat`, `model-check`, `config`, and `doctor` already exist as documented elsewhere. `model-check` is a synthetic read-only provider/tool contract check. Omitted required inputs trigger questions, never guesses. Exit codes distinguish verified success, failed task, cancellation and setup errors. Support spaces in Windows paths and UTF-8 output. Interactive approval is unavailable in noninteractive runs, so approval-required actions stop.

## Input/tool contract

CSV analysis accepts repeatable `--numeric-column <header>` selections to calculate exact decimal totals. Selected header names and totals are included in structured exports; source row values remain excluded. Selected names are hashed into the checkpoint state, and `resume` requires the same selections. Runs without selected columns retain the original state hash and can resume with the existing `--input` form.

`taskforge run document-convert --input <path> --output <new.txt>` extracts bounded plain text from an explicitly approved TXT, Markdown, text PDF, DOCX, or XLSX input. It shows the extracted text, requires persistent write approval for the output folder and exact path/content-hash confirmation, creates only a new file, and stores a metadata-only artifact reference linked to the document-analysis run. Conversion output is limited to 64 KiB; spreadsheet cells are rendered as escaped tab-separated rows. No source or converted text is stored in MongoDB.

`taskforge run document-analyze --input <path> [--output <new.json|new.csv|new.md>]` optionally exports validated document format/count metadata. It excludes document text, absolute paths, spreadsheet names, and cell values; requires persistent folder write approval and interactive preview/hash confirmation; creates a new file only; and links its hash, relative filename, type, and byte count to the completed document run.

`taskforge run research --query <question>` requires an interactive confirmation before sending that exact bounded query to Groq browser search. The `--compare <question> --against <question>` form confirms both exact queries and performs two separate searches. It displays both unverified model summaries, bounded source excerpts and URLs, and identifies exact shared URL matches only; it does not infer claim-level agreement or contradiction. Both modes support only Groq's currently documented GPT OSS browser-search models, have no additional API key, validate bounded HTTPS source metadata, terminal-escape returned text, and do not persist. Noninteractive runs stop before provider access. Search is optional and subject to the configured Groq account's service limits and pricing.
`taskforge run draft --input <draft.json> --output <new.md>` accepts a bounded JSON object for a GitHub issue draft or email draft and creates a new Markdown artifact after explicit content preview and path/hash approval. It has no external write integration and never sends. The selected Markdown format is a local implementation convention; no email provider or GitHub write credential is used. Create-only protects against overwriting a target occupied at link time; concurrent hostile replacement of the approved parent directory is not protected by Node's path-based filesystem API.

`taskforge run specialist-review --root <directory> --file <relative-path> [...]` accepts up to five locally approved source files and a user-provided goal, then makes up to 40 provider requests across at most two fixed specialist roles and one parent review. One `AgentBudgetLedger` is shared across worker tool loops and parent review, capped at 30 actions. Workers receive one fixed `search_approved_source` tool that performs literal case-insensitive search only over the already approved, read, heuristically redacted excerpts; each query is limited to 200 characters and each result to 20 matching lines/8,000 characters. The parent review receives no tools. Nested spawning and other tools are unavailable. Worker and parent findings are bounded and labeled unverified; incomplete provider/budget work returns a failure status and nonzero CLI exit. Files/results are not persisted. No filesystem reread, browser, shell, GitHub-write, or email-send access is available.

Validate task inputs and tool arguments with runtime schemas. Every tool declares name, description, input schema, access requirements, effect classification, timeout and output limits. Reject unknown tools and invalid arguments. Tool results include status, evidence and bounded output. Treat model responses as untrusted input. Include idempotency identifiers for operations where supported. Persist action intent before mutation and outcome afterward.

## Provisional run budgets
30 tool actions; 40 model requests; 15 minutes of active runtime excluding approval waiting; 3 equivalent consecutive failures. Limits apply across parent and workers, not per agent. Maximum two workers; bounded context and tool-output sizes. Stop at a limit, save progress and offer a deliberate extension. Provider spending ceiling only when usage/pricing can be measured; do not promise exact costs from a request count. Provider quotas remain independent.

## Cancellation and recovery
Ctrl+C requests cancellation, stops new actions, aborts supported requests and terminates child processes with a bounded grace period. Record cancelled or uncertain outcomes. Preserve completed artifacts. Resume validates checkpoint version and current inputs and requires fresh approvals where necessary. Cancellation cannot reverse an already completed external action.

## History recommendation
Save detailed run summaries and redacted, truncated tool events by default, not full chats. Full transcripts are opt-in with disclosure. Proposed defaults: raw events/transcripts expire after 30 days, summaries after 90 days, maximum 5 MB stored event/transcript payload per run; oversized outputs become local artifacts. Artifacts have separate cleanup rules and no implicit TTL deletion. Secret redaction precedes persistence. User deletion removes a run's database records and only its owned artifacts when explicitly requested.

## Checks by capability
Files: path escape, junctions, secret filtering, unchanged-content moves, duplicate-name conflicts. Data: known totals, duplicates, missing values, encodings and malformed CSV. Software: reproduce seeded regression, inspect approved diff and rerun relevant tests. Browser: controlled HTTP errors, failed requests, console failures, broken link and mobile overflow; login checks only with supplied accounts. Research: sources actually retrieved, timestamps, contradiction/unsupported-claim handling. Agents: budget sharing, denied tools, write conflicts and parent review. Scheduling: missed runs, duplicate suppression and approval-required state.

## Persistent folder approvals

Persistent folder grants use `permissions approve --root <folder> --access <read|write>`, `permissions list [--all]`, and `permissions revoke --root <folder> --access <read|write>`. The CLI canonicalizes an existing non-sensitive directory and asks interactively before granting or revoking. The selected TaskForge store records each access scope separately and retains revoked entries. File and repository workflow entry points require a covering active grant for their canonical root/path and required scope, then continue to require operation-specific confirmation. Grant lookup failure or database unavailability denies access. Secret paths and symlink/junction escapes remain denied by the path policy. Local-store Windows ACL and full workflow parity acceptance remain pending.

## Security and privacy
No credentials in logs, screenshots intended for sharing, reports, fixtures or Git. Explicit online-transfer disclosure and user choice. Restrict network destinations where needed; protect against private-network access when processing untrusted URLs. Browser tests against localhost require explicitly approved local targets. Avoid rendering untrusted HTML directly into reports. No claim of comprehensive penetration testing or security certification.

## Distribution
Document tested Node version, MongoDB installation/connection, local model and browser setup on Windows. Pin dependencies and commit lockfile. npm package must declare actual files, executable and engine requirements. Validate tarball on a separate Windows consumer project before publishing. MIT covers TaskForge code, not automatic relicensing of model weights or dependencies.

## Local scheduling
`taskforge schedule add --workflow <csv-analyze|document-analyze> --input <path> (--once <future-UTC-ISO>|--every-minutes <1..10080>)` stores a schedule in the selected TaskForge store. The foreground `schedule run` process is the only executor; no OS scheduler integration is installed. The process claims due records atomically, records and skips elapsed intervals outside a 30-second grace period, and marks approval-required occurrences pending when no user is present. Every run requires new interactive approval and exact-file read consent, rechecking the path before reading. `schedule list`, `pause <id>`, `resume <id>`, and confirmed soft-delete `delete <id>` are supported. `schedule run --once` performs one scheduler tick for verification/operations. SQLite full scheduling workflow parity remains acceptance pending.


## Approved file move

taskforge run file-move --source <file> --target <new-file> requires persistent read and write grants for the source folder, a persistent write grant for the destination folder, and interactive confirmation of both canonical paths and source SHA-256. It supports matching TXT, Markdown, CSV, PDF, DOCX, or XLSX suffixes. Destinations must not exist. The implementation creates and verifies a same-volume hard link before deleting the source; cross-volume moves are unsupported. A failed operation attempts to remove only a destination whose file identity matches the opened source.


## Loopback browser audit reporting

The local run browser-audit result reports the checks attempted and their aggregate findings: HTTP errors, failed same-origin browser requests excluding policy aborts, bounded local link failures, console/page errors, images missing alt text, unnamed visible controls using an accessible-name heuristic, horizontal overflow at 360px and 1280px viewports, and presence of CSP, X-Content-Type-Options and Referrer-Policy headers. Mixed-content inspection is marked skipped because the accepted target is HTTP loopback. Navigation, DOM or design observation failure marks the MongoDB run failed and the CLI exits 3. The CLI displays at most 32 bounded CSS custom-property names and semantic component counts; those observations, page content, URL, link, screenshot, and console text are not persisted. This does not establish WCAG conformance, broad security coverage, or original design-token recovery.


## Targeted software checks

`run software-check --root <directory> --check node-test --test <relative-file>` permits one explicit `.js`, `.cjs`, or `.mjs` test file beneath the approved root. The command rejects absolute paths, paths outside the approved root, missing files, unsupported suffixes, and symbolic-link test files. The selected file is shown in the interactive command approval. Full-suite `node --test` and `typescript-check` retain their existing behavior. `typescript-build` invokes only the repository-local compiler; emitted files and build info go to a newly created `.taskforge-build-*` directory under the approved root for dependency resolution. The runner removes its directory after success, failure, timeout, or cancellation only when its UUID-bound owner marker and generated-only contents still validate; otherwise it preserves the directory. At build start, only directories older than 24 hours with a matching marker, confirmed-dead PID, and generated-only regular-file contents can be reaped. Unknown, active, malformed, symlinked, or mixed-content directories are retained. Configured `outFile`, trace, and CPU-profile outputs are rejected. No additional test-runner arguments are accepted. All commands execute repository code/configuration and are not an OS sandbox.

## Recovery scope update - 14 October 2026

`run browser-audit --url <https-url> --journey <json-array>` supports exact visible-text expectations, constrained same-origin GET search, classified same-origin link navigation, opening the first visible Harry Potter result link, and browser back, after interactive approval of the exact target, journey, and up to seven additional HTTPS origins. Page-provided links are followed only for recognized content-route roots without mutating route terms; unsupported or suspicious destinations are skipped with a reason. This is a conservative heuristic and cannot establish server-side GET semantics. Every audit automatically performs a bounded diagnostic pass: initial/final DOM snapshots (at most 2,000 elements and a 240-character text sample each), up to two viewport screenshots (4 MiB per image), console/page errors, approved-origin response and failed data-request observations, and at most ten final-page same-origin HEAD route probes with redirects not followed. Snapshot traversal truncation is explicit, and truncated evidence cannot support empty-page or missing-results conclusions. Password-field detection traverses at most 2,000 DOM elements and counts at most 20 password fields before failing closed. Screenshots are saved in a generated OS temporary folder; screenshots and DOM samples are not persisted or sent to a model. MongoDB retains aggregate status only. The public browser uses a fresh unauthenticated context and DNS-pinned egress; private/internal addresses, unapproved origins, WebSockets, non-GET/HEAD methods, form submissions, and requests beyond configured limits are blocked. A visible password gate stops journey actions. Reports separate observed failures from suspected causes. Additional origins are suggested only for valid public HTTPS data origins when blocked fetch/XHR activity coincides with missing result cards after complete DOM sampling and no authentication gate; origins remain untouched until a new exact approval. Page content is untrusted and cannot expand permissions. These heuristics are not a comprehensive security or accessibility audit. Live acceptance remains pending because the approved unauthenticated `/discover` route reaches `/login`.

Top-level public document navigations use `route.fetch({ maxRedirects: 0 })` and block every HTTP redirect before Chromium follows its `Location`; this prevents a resource-origin approval from implicitly authorizing top-level navigation. Redirect destinations are not accessed, even when same-origin, so server-side redirect-based login and CDN flows are unsupported and reported as coverage limitations. The egress proxy continues to enforce DNS and origin policy for all browser traffic. Page-script GET endpoints can still have server-side side effects despite method and route heuristics; the report must not claim a read-only guarantee beyond the requests and actions TaskForge itself controls.

`run data-specialist --input <file> --goal <question>` supports locally parsed CSV, XLSX, text PDF, DOCX, TXT, and Markdown. It previews bounded heuristically redacted evidence before separately approved transfer; local paths and filenames are excluded. The browser `--specialist` option transfers aggregate evidence only. Specialist and parent requests share budgets, use the selected provider without switching, and require parent review. Results are unverified and not persisted.

At the time of this recovery note, MongoDB was the only implementation and those four items had proposal status. The later approved development scope below supersedes that proposal status; the capability audit remains the authority for what is currently implemented. Deployment actions remain deferred and the independent developer trial remains pending.

## Approved development scope and acceptance contracts - 14 October 2026

The owner subsequently approved all 11 development areas listed in `prd.md`; this section supersedes the previous paragraph's proposal status for local storage, guided setup, architecture analysis, and read-only deployment tracing. The current implementation remains the baseline in `CAPABILITY_AUDIT.md`; this approval is not evidence that any new area is implemented.

1. **Natural language and chat:** accept one bounded goal, resolve only validated registered workflows/tools, ask rather than guess missing inputs, show the resolved plan and data destination, obtain required approvals, return evidence-backed status; interactive chat retains session context and can continue approved tools under shared budgets. Tests cover ambiguous/unknown intent, missing inputs, consent refusal, provider failure, cancellation, and no unapproved tool invocation.
2. **Investigation and changes:** inspect only approved project paths; produce a content-bound diff/preview; require distinct approval before writes; run only relevant fixed, approved verification; report diff, command, result and limits. Synthetic seeded-bug integration tests prove denial leaves bytes unchanged and approval applies only the reviewed preview.
3. **Task registry:** built-ins are versioned local definitions with runtime-validated instructions, input/output schemas, tool requirements, examples and tests. The registry rejects malformed/unknown definitions and tools; its contents cannot expand the central permission registry. No arbitrary third-party executable definitions.
4. **Research:** retrieve actual sources through the configured approved provider, retain source URL/title/date and bounded supporting evidence for each comparison claim, cite claims, label uncertainty and failures, and do not persist query/source content unless a documented approved setting says so. Deterministic fixtures validate URL/content provenance, escaping, partial failure and citations; a live provider check verifies actual retrieval without claiming provider permanence.
5. **Browser/specialist acceptance:** preserve fresh ephemeral browser contexts and manual owner login; no personal-profile import. Fixture acceptance covers the supported journey and auth boundaries. BookFinder search/results/details/back is a separate owner-operated gate and is pending until the approved login/journey can actually be completed.
6. **Run lifecycle:** define terminal/interrupted/uncertain states, cancellation effects, history retention/deletion and resumable workflow/input hashes. Test Ctrl+C at approval, read, mutation and verification boundaries, stale-state rejection, safe replay, database failure and history redaction. Do not claim universal cancellation or resume until every advertised command has evidence.
7. **Human acceptance:** owner walkthrough uses synthetic fixtures. Independent developer trial must be performed by another developer from documented clean Windows setup; agent review is not a substitute.
8. **Persistence:** local storage is the new-install default. MongoDB remains an explicitly selected optional adapter. Never fall back between backends on failure; never migrate, delete or overwrite existing Mongo data automatically. Backend contract tests cover parity for required records, transaction/failure behavior, schema versions and redaction.
9. **Setup/distribution:** guided setup validates Node/runtime and selected provider/storage, redacts diagnostics and does not silently provision services or fetch models. Windows artifact includes its required runtime and passes clean-machine install, launch, upgrade/side-by-side, package-content and uninstall/data-retention checks. No credentials, session state, or private artifacts ship.
10. **Architecture analysis:** consume only user-approved repository roots and selected files; tie every finding and diagram node/edge to inspected file/line evidence, label inference and coverage, redact secrets, and never execute source. Fixtures cover incomplete/unsupported projects and misleading evidence.
11. **Deployment tracing:** read-only authorized GitHub/Vercel access only. Scope exact account/project/repository, minimum read permissions, redacted credential handling, bounded requests and explicit source links for each deployment/build/environment conclusion. Tests prove no write API is called and missing/denied access returns blocked, not success.

All tool arguments, task definitions, provider responses and external data are untrusted and require runtime validation. Preserve strict TypeScript, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes`; no explicit/implicit `any`, `@ts-ignore`, permission bypass, provider switch, unrestricted shell, silent provider/storage fallback, sending, publishing, purchases, or deployment actions. Groq remains default. Shared worker budgets cover parent and all specialists. No paid services or model downloads without later owner authorization.
