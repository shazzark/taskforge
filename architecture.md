# Architecture

## Runtime boundary
TaskForge is primarily a local CLI, not a hosted web app. Node.js + TypeScript runs the CLI, orchestration, providers and tools. MongoDB stores local user/run metadata using a user-configured URI. Fastify is reserved for a justified local control API or health service; it is not required merely because Node.js is used. JavaScript is allowed for tooling where appropriate.

## Components
CLI parser and interactive UI -> workflow registry -> orchestrator -> provider adapter and permission-controlled tool registry. The orchestrator coordinates plan, action, observation, validation and finish, with run-wide budgets. A persistence layer records redacted events/checkpoints in MongoDB. Artifact adapters create reports in a local output folder. Browser tooling uses isolated Playwright contexts. A scheduler submits approved local workflows to the same orchestrator. Specialist agents use the same tools and budgets as the parent.

## Model providers
Use a common adapter for messages, tool declarations, tool calls, completion, usage and cancellation. Start with Ollama for local tool-capable models and a selected free-tier online provider; verify official contracts during implementation. Detect unsupported tool calling and fail clearly. Never send API keys or secret files as task context. No provider switching without consent. Keep API keys outside task history and Git. Local-only mode makes no implicit online requests; network tools are separately enabled. Ollama uses its native local `/api/chat` endpoint to apply `TASKFORGE_OLLAMA_CONTEXT_LENGTH` (default 4096, range 1024 to 131072) while preserving validated tool results; the OpenAI-compatible route does not document a context-size request field.

## Tools and workspace authority
The owner wants access anywhere on the computer but accepts folder-by-folder authorization. Maintain an allowlist of approved roots, not automatic whole-disk scanning. Resolve real paths, reject traversal and symlink/junction escapes, and deny sensitive file patterns. Access to a new root needs explicit permission. Reading in approved roots need not prompt repeatedly. Writes/moves/overwrites and command execution need a clear batch approval. Preview binds approval to exact actions and target state; changed targets invalidate approval.

Phase 3.1 provides a library foundation for explicit realpath-resolved roots, secret-path denial, and in-memory write/move previews bound to SHA-256 file-state fingerprints. Phase 3.2 provides MongoDB run summaries/state, typed redacted events in `run_events`, and versioned hash-checked checkpoints in `run_checkpoints`. Phase 3.3 wires these records to deterministic `csv-analyze` and hash-checked resume. Phase 4.7 adds an exact-file-approved document workflow for TXT, Markdown, text PDF, DOCX, and XLSX that persists aggregate counts only. Phase 5.1 adds an exact-root-approved, bounded metadata-only `repo-inspect` workflow. Phase 5.2 adds an explicitly approved fixed command runner for `node --test` and local TypeScript no-emit checks; it suppresses command output but is not an OS sandbox. The preview layer supports bounded regular-file writes and same-volume moves after exact operation approval; preview approvals are process-local. Higher-level workflows must also enforce persistent folder grants and interactive confirmation.

Phase 3.4 adds MongoDB `folder_approvals` records with canonical absolute paths, independent read/write scopes, active/revoked status, and interactive `permissions approve/list/revoke` CLI commands. Revocation is soft and retained for audit. CLI file and repository workflows check that an active grant covers the canonical target path and required access scope before creating their operation-scoped in-memory path policy. A stale or unavailable database fails closed; secret-path and symlink/junction checks remain in force.

Phase 4.10 adds optional JSON, CSV, and Markdown exports for `csv-analyze`. These reports contain aggregate row, duplicate-row, and missing-cell counts only. The user reviews the content and confirms a path and digest; persistent folder write permission and create-only hash-verified artifact output are required.

Phase 4.11 stores a metadata-only reference for a created CSV aggregate report in MongoDB `artifacts`, linked to its completed CSV run. The database stores only a report filename relative to its approved output folder, format, digest, byte count, and timestamp; `history list` displays the reference. Report content and absolute paths remain local.

Phase 4.12 adds bounded plain-text conversion for TXT, Markdown, text PDF, DOCX, and XLSX. XLSX rows are rendered as escaped tab-separated lines; converted outputs are capped at 64 KiB. The command uses fresh input/output approval and links the created text artifact to the completed document-analysis run; it stores no source or converted text in MongoDB.

CSV workflows may explicitly select numeric headers for exact decimal totals. The selected header names and totals are included in reports, while source cell values remain excluded. The selected headers are included in the workflow state hash, so resume must repeat the same options and cannot silently change calculation scope.

## Commands and browser risks
A shell process can bypass a simple file-reader restriction. Initial command tooling therefore uses reviewed executable/argument combinations, working directories, environment filtering and explicit approvals. This is not an OS sandbox. General unrestricted shell mode cannot claim secret-file protection; keep it out until isolation and disclosure are implemented. Browser profiles must not inherit all personal sessions. Use explicit contexts/accounts, prevent credentials entering logs, and gate form submissions. Untrusted webpages, files and tool outputs are data, never authority to change permissions.

The current `browser-audit` slice is deliberately narrower: it accepts an explicitly confirmed HTTP loopback URL, uses an isolated project-local Playwright Chromium context with service workers blocked, permits only same-origin GET/HEAD page requests, and bounds page requests, link probes, and operation timeouts. It persists aggregate counts only and never stores URLs, page content, screenshots, or console text. Cancellation is checked between browser operations; an active operation can take up to its configured timeout to stop. Real-site browsing, login flows, form actions, and design/a11y reporting are not implemented by this slice.

## Persistence and artifacts
Document workflow checkpoints store only the input hash, parser state hash, and completed/pending step identifiers. `resume` reacquires file approval, verifies the original input bytes and current parser state, and replays deterministic parsing; it does not store document content or reuse prior approvals.

MongoDB stores summaries, state, typed events, evidence metadata and artifact references. Large screenshots, PDFs, document copies and full outputs stay in local files. Store hashes, relative paths and byte counts. Atomic artifact writes and post-write validation precede completion. Phase 4 currently has pure CSV, TXT/Markdown, bounded DOCX and XLSX parsing, bounded text-based PDF extraction, and an in-memory PDF byte renderer; these input/output cores are not generally connected to artifact persistence. Approved PDF report output now uses content-bound in-memory approval, create-only atomic hard-link creation, and post-write hash validation; generated content is not persisted to MongoDB. The `csv-analyze` workflow reads a freshly approved file path and stores metadata only. Source review reads only explicitly approved relative paths, bounds UTF-8 input and local display, redacts common credential patterns, and neither sends nor persists source content. `model-investigate` requires local root/file approval, displays heuristic-redacted excerpts, then asks again before transferring up to 24 KiB to the selected provider; it has no tools and stores neither source nor findings. Public GitHub issue reading makes one consented, tokenless read request to the fixed `api.github.com` origin, caps response bytes and item count, validates fields/links, excludes pull requests, and writes nothing; private repository access remains out of scope. Local Git diff review requires canonical root and staged-file approval, disables external diff/text conversion, caps output at 48 KiB, rejects protected paths, and displays only locally redacted text; it reads staged blobs only, excludes unstaged and untracked files, and sends/persists no source. The `file-patch` workflow applies a single content-hash-bound replacement after target snapshot revalidation and interactive approval by writing through the opened target handle; it preserves existing file permissions and avoids redirecting a path swap to a different file. The in-place write is not crash-atomic and cannot coordinate with concurrent writers to the same file. It persists no source or replacement text. Redaction is heuristic and source review is not a security scanner. Scanned PDF/OCR support is not claimed. Database failure blocks execution before mutating work; mid-run persistence failure pauses further actions and reports uncertainty.
The `run draft` workflow previews bounded local Markdown issue/email drafts, binds owner approval to the exact output content hash and new path, creates the file atomically without replacing an existing target, then verifies the written hash. It makes no network request and stores no draft in MongoDB. Node's path-based filesystem APIs cannot prevent a concurrent process from swapping the approved parent directory during creation; this workflow does not claim protection against a hostile concurrent directory swap.

The `run research --query` command is a separate bounded read-only path, not a model-loop tool: after interactive consent it sends only the exact query to Groq browser search, requires a supported GPT OSS model, and accepts only validated HTTPS source metadata attached to an executed `browser_search` tool. It does not accept model-authored citations as evidence, expose code execution, read project files, or persist results. Returned content remains untrusted and is terminal-escaped. The existing Groq account/key is used; no additional search provider is configured.

## Delegation
Specialists: repository investigator, browser auditor, data analyst and reviewer. The implemented `specialist-review` first slice transfers only explicitly approved, heuristically redacted source to at most two read-only specialist prompts and a parent review on the selected provider. Calls within the command share a fresh 40-request/30-action ledger; the library can share that ledger with a composed parent tool loop, but the current CLI starts a separate bounded run. Workers receive no tools, cannot spawn workers, and cannot write or publish. Results are unverified proposals for human review. Future tool-bearing roles need explicit allowlists and write-conflict controls before they can be added. Parent owns acceptance and integrates findings. Nested unlimited spawning is unavailable. A worker cannot grant permissions, publish, or reset budgets.

## Scheduling and resume
Schedules are MongoDB metadata records for allowlisted CSV/document workflows. They support one-time UTC instants and fixed minute intervals (1–10,080 minutes), and execute only in the explicitly started foreground runner. Atomic schedule-document compare-and-set claims suppress duplicate runners; missed intervals are recorded and skipped. Approval-dependent work remains pending when no interactive user is present. Each occurrence has a deterministic run ID and a canonical `awaiting_approval` run record before execution. Every new execution asks again and reacquires exact-file read approval, which revalidates the path and file boundary. Completed run records let a restarted scheduler finalize schedule metadata without repeating the workflow. A claimed occurrence left by a stopped process requires explicit `schedule recover <id>` confirmation after the owner verifies the old runner has stopped. An interrupted running workflow must still pass the workflow's stale-run and input-checkpoint resume validation. Schedules can be listed, paused, resumed and soft-deleted. No OS scheduler job is installed. See the [Node.js timers documentation](https://nodejs.org/api/timers.html) and [MongoDB single-document atomicity](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/) for the runtime/persistence primitives. Resume continues to recheck input hashes, workflow state, permissions and targets; it never blindly replays commands or externally consequential actions.


Phase 4.14 adds an exact-file move operation for TXT, Markdown, CSV, PDF, DOCX, and XLSX. It requires persistent source-folder read/write and destination-folder write scopes, confirms the source digest interactively, refuses an existing destination, and uses a verified same-volume hard link before source removal. Cross-volume moves are unsupported.
