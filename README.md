# taskforge

A terminal assistant for a fixed set of explicit, approval-controlled developer workflows, with optional bounded model features.

**Status:** TaskForge is in early development. Bounded file/data, software, local browser fixture, research, GitHub-read, local-draft, schedule, specialist-review, and dedicated ephemeral manual-login workflows are implemented. A bounded single-file agent replacement preview, research citation provenance, Phase 15.1 document checkpoint binding/history-list coverage, Phase 15.2–15.4 CSV/document cancellation and resume coverage, fixed-adapter execution for eligible installed CSV and supported-document tasks, and a read-only `setup` guide are implemented; acceptance remains open for the broader phases. Public-site journeys remain read-only and require explicit approval. The latest full serial suite passed on 2026-10-19 (223 passed, zero failed or skipped) against isolated local storage and a dedicated loopback MongoDB test database; see `task.md` for recovery and verification boundaries. Owner-operated live provider/TTY, Groq intent/citation, BookFinder, remaining Windows storage/package gates, and the independent developer trial remain pending.

**Current capability boundary:** Named workflows remain available through `run <workflow> ...`. `do "<instruction>"` and `chat` expose fixed CSV/document tools plus a constrained installed-task adapter for validated definitions matching the fixed CSV or supported-document workflow. Each file operation still requires exact-file and stored-folder approval; document results contain counts only. Task definitions do not provide code, permissions, or extra capabilities, and unsupported task types remain unavailable. `run agent-fix --root <directory> --target <relative-source> --goal <instruction> --test <relative-test.mjs>` can request a single full-file replacement through the configured provider, show a hash-bound preview, and apply only after explicit approval. It requires TTY, persistent read/write grants and separate provider-transfer, patch and test approvals; it refuses credential-like source/candidate text. Multi-file diffs, broader automatic workflow choice, and live TTY/provider repair acceptance remain unverified. Groq remains the default; consent covers user instructions and approved aggregate/source data as described in each command. New installations select local SQLite; a configured Mongo URI continues selecting MongoDB unless explicitly overridden. Cross-backend parity, Windows privacy/durability and packaged-runtime acceptance remain pending; there is no migration or fallback. Providers are Groq and loopback-only Ollama. Authenticated browser checks use a fresh ephemeral manual-login context without importing profiles or sessions. `run architecture-report` provides bounded reports and a cited Mermaid import graph for explicitly selected files. Line-based JS/TS and Python import evidence is supported, with relative imports resolved heuristically only against selected files; broader language coverage, aliases, dynamic/multiline imports, and package/compiler resolution remain unimplemented. `run deployment-trace` has bounded read-only GitHub/Vercel adapters and fixture coverage; live Vercel project access remains pending exact owner-selected scope and local token setup. Existing repository inventory, public issue reading and website auditing remain distinct narrower features. Other approved work, external acceptance, and the independent developer trial remain pending. See the [capability audit and owner testing walkthrough](CAPABILITY_AUDIT.md) and [implementation plan](implementation-plan.md) for exact gates.

## Local development

`run research --query "..."` sends only the approved query to Groq's built-in browser search after an interactive prompt. Citation output is enabled; valid inline source markers are mapped to validated returned URLs/excerpts, unmapped markers are flagged, and sentences without inline markers are reported heuristically. `run research --compare "..." --against "..."` performs two separate searches and shows each cited answer, retrieved excerpts and exact shared URLs. Shared URLs do not establish agreement, and source mapping does not prove that an excerpt semantically supports a claim; answers remain unverified. Both modes persist nothing and use the existing Groq configuration; see [Groq Browser Search](https://console.groq.com/docs/tool-use/built-in-tools/browser-search) and [Groq citation options](https://console.groq.com/docs/api-reference) for current limits and service details.

Contributor setup and review expectations are in [CONTRIBUTING.md](CONTRIBUTING.md).

The `run browser-audit --url <loopback-url>` slice is available for explicitly approved local HTTP fixtures. It uses isolated Chromium, blocks cross-origin and unsafe-method requests, and reports HTTP/request/link errors, console/page errors, basic accessibility heuristics, mobile/desktop overflow and selected passive response headers as aggregate findings. It also displays bounded CSS custom-property names and semantic component counts locally; these observations are not persisted. Mixed-content checks are skipped for HTTP fixtures. `run research --query <question>` uses Groq browser search after interactive consent and persists nothing.

Public browser journeys use `run browser-audit --url <https-url> --journey '<json-array>' [--origin <https-origin>]...`. The CLI displays and asks to approve the exact target, journey, and additional origins before navigation. Each audit autonomously captures up to two local screenshots, bounded initial/final DOM summaries with short text samples, console/network failures, and same-origin HEAD route probes. Truncated samples are marked incomplete and do not support empty-page or missing-results conclusions. Observed failures and suspected causes are reported separately; page content is untrusted and cannot change permissions. Supported steps are `expect-text`, a one-field same-origin GET `search`, `open-first-book` (the first visible same-origin link named for “Harry Potter”), classified read-only same-origin `click-link`, and `go-back`. Page-provided links outside recognized content routes or with mutating route terms are skipped, and same-origin requests whose paths/parameters contain mutating terms are blocked. This conservative classifier cannot establish server-side GET semantics. Top-level HTTP redirects are fetched one hop at a time and blocked without following; redirect-based login/CDN flows are reported as unsupported coverage. Forms are never submitted. Each requested visible target gets a bounded wait (up to 2.5 seconds); a visible password field stops the journey. Screenshots/DOM evidence stay local; The selected store holds aggregate metadata only, and specialist transfer excludes page content. The unauthenticated browser blocks private/internal egress, non-GET/HEAD methods, WebSockets, unapproved origins, and over-budget traffic. Blocked origins are never accessed automatically; additional approval is surfaced only for blocked data requests plausibly related to missing results after complete DOM sampling and no authentication gate. Coverage remains heuristic and is not a comprehensive security or accessibility audit.

For an owner-operated authenticated read-only journey, add `--manual-login` to the same command. TaskForge opens a fresh headed Chromium context without a personal profile or imported browser state. It does not capture authenticated-page screenshots, DOM text, responsive/accessibility/design details, or specialist evidence; the browser context and cookies are discarded on close. The owner enters credentials in Chromium. Additional HTTPS origins require approval before access, and a query-free POST to a recognized authentication path is paused for exact per-request approval. Authentication path names do not prove server-side behavior. Redirect responses from authentication POSTs are blocked before following them; redirect-based login flows are unsupported. After a successful non-redirecting login response, TaskForge closes the authentication-action window, settles the page, then asks the owner to approve the exact read-only journey separately. Other unsafe methods, query-bearing authentication POSTs, and later POSTs are blocked. The site may retain its own server-side login state. Manual login is not a security audit.

`run data-specialist --input <file> --goal <question>` parses supported CSV, XLSX, PDF, DOCX, text, or Markdown locally, previews bounded heuristically redacted evidence, and requires explicit provider disclosure and transfer approval. The browser command's optional `--specialist` transfers aggregate audit evidence only. Both use the configured provider (Groq remains default), bounded shared specialist budgets and parent review; outputs are unverified and not persisted. Online transfer requires separate approval. Do not supply sensitive content unless its transfer is approved.

`resume <run-id> --input <path>` supports uncertain CSV and document analysis runs. It asks for approval to read the exact file again and resumes only when its bytes and workflow state match the persisted checkpoint. CSV state includes selected numeric columns; document state includes the normalized format. A document checkpoint created by the prior format-agnostic hash is rejected safely and retained.

`history list` shows at most the newest 50 redacted run summaries and artifact metadata. The selected store retains older records; there is no history delete command or automatic purge. Chat transcripts and source/browser contents are not saved as history. Ctrl+C is handled only by commands with signal-aware paths; it cannot undo an operation already applied, and a crash or interruption during a write may leave uncertain state. There is no general `cancel <run-id>` command. See [the lifecycle audit](LIFECYCLE_AUDIT.md) for per-workflow cancellation and resume boundaries.

Requirements: Node.js 22.13.0 or later and npm.

Try natural-language CSV analysis from the repository root:

```powershell
node dist/cli.js do "Analyze examples/amounts.csv and report the row count and exact total of the amount column."
```

The sample has two rows, and the exact `amount` total is `20`. The command requires a configured provider; Groq asks for permission before sending the request and approved aggregate to the remote provider. Approve the exact file when prompted. This example is a user trial, not recorded owner acceptance.

`run document-analyze --input <path> [--output <new.json|new.csv|new.md>]` can write a metadata-only aggregate report. The export shows format and parser counts; it excludes document text, paths, sheet names, and cell values. Output requires a persistent folder write grant and interactive preview/hash approval, creates a new file only, and links a metadata-only artifact reference to the completed run. Without `--output`, the command only displays the analysis summary.

`run software-check --root <directory> --check typescript-build` executes the repository-local TypeScript compiler after explicit root and command approval. Emitted files and build info go to a newly created `.taskforge-build-*` folder under the approved root so generated ESM can resolve repository dependencies. TaskForge removes its exact folder after success, failure, timeout, or runner-handled interruption when the ownership marker and generated-only contents still validate; if they do not, it preserves the folder. A later build reaps only old, UUID-marked directories whose owner process is gone and whose contents match generated output types; uncertain artifacts are retained. The folders are Git-ignored and excluded from the npm package allowlist. Configured `outFile`, trace, and CPU-profile outputs are rejected. `typescript-check` remains no-emit; Node test commands retain their fixed runner and output-suppression behavior. Repository code and build configuration are executable inputs, so these commands are not an OS sandbox.

Folder approval records are stored in the selected TaskForge database and enforced by file workflows. Grant a canonical folder scope with `permissions approve --root <folder> --access <read|write>`, inspect it with `permissions list [--all]`, and revoke it with `permissions revoke --root <folder> --access <read|write>`. Read workflows require a covering read grant; file patching requires both read and write; artifact creation and repository command execution require write scope. Each workflow still asks for its separate operation approval, and protected secret paths remain denied. Revoked records remain visible to `permissions list --all` and do not block future grants.

The CLI supports the documented file, data, software, local browser fixture, research, public GitHub read, local draft, foreground scheduling, and specialist-review workflows. See `task.md` for verified scope and limitations. Configuration reads `TASKFORGE_STORAGE`, optional `TASKFORGE_MONGODB_URI`, and `TASKFORGE_PROVIDER` from the process environment or ignored repository-root `.env`; new installs default to local SQLite, and a configured MongoDB URI preserves existing MongoDB selection when storage is not explicit. `config` and `doctor` report the selected backend without revealing its path or URI. `config` validates settings and prints a redacted summary. `doctor` checks the selected database but does not contact the model. `model-check` sends a fixed synthetic prompt to the selected provider and verifies one read-only fixture tool call. `chat` is interactive and bounded. `chat` and `do "<instruction>"` expose only the fixed `analyze_csv` and `analyze_document` agent tools, which require exact-file approval and an existing persistent read-folder grant. Document tool output contains format/count aggregates, not extracted content. Groq asks before sending messages and approved aggregates (including selected column labels, excluding source rows and extracted document text); local Ollama does not send this content to a remote model provider. `csv-analyze` reads one approved input file. `document-analyze` reads one approved TXT, Markdown, text PDF, DOCX, or XLSX file, then stores aggregate counts only. `pdf-report` reads approved JSON and writes a new PDF only after showing the output path and hash for confirmation; it never replaces an existing file. `repo-inspect` asks before inventorying one exact root and records bounded metadata only; it does not read source contents or run commands. `source-review` requires approval of an exact root and explicit relative file list, then displays bounded source locally after common credential-pattern redaction; it neither sends nor persists source contents. Redaction is heuristic, so review displayed source before copying it elsewhere. `model-investigate` displays up to five selected source excerpts after heuristic redaction and requires a second explicit confirmation before sending those exact excerpts to the configured provider. It offers no tools, does not persist excerpts or findings, and labels the response as unverified. `github-issues --repository owner/name` asks before making one public read-only API request, uses no token, and displays at most 20 open issue titles (pull requests are excluded). Public reads are limited by GitHub's unauthenticated API quota. `file-patch` requires approval for an exact root, target, and replacement file, shows redacted before/after text and a SHA-256 hash, and revalidates the target before writing through the approved file handle. It preserves the existing file identity and permissions, but the in-place write is not crash-atomic and cannot coordinate with another process concurrently editing that same file. `file-move` requires persistent source-folder read and write grants and destination-folder write grant, plus interactive confirmation of exact paths and source hash. It supports matching TXT, Markdown, CSV, PDF, DOCX, or XLSX suffixes, refuses existing destinations, and uses a verified same-volume hard link before removing the source; cross-volume moves are unsupported. `git-diff` asks for approval of the canonical repository root and exact staged tracked file list, then displays up to 48 KiB of locally redacted diff. It excludes unstaged and untracked files and refuses protected secret paths; the redaction remains heuristic. `software-check` requires separate root and check approval, then runs only `node --test` (the full suite or one selected in-root `.js`, `.cjs`, or `.mjs` test file), local TypeScript `--noEmit`, or the repository-local TypeScript build with output constrained under the approved root; it does not display or persist command output. These checks execute code from the approved repository and are not an OS sandbox. Use `TASKFORGE_PROVIDER=groq` with `TASKFORGE_GROQ_API_KEY` and optional `TASKFORGE_GROQ_MODEL`, or `TASKFORGE_PROVIDER=ollama` with `TASKFORGE_OLLAMA_BASE_URL` and `TASKFORGE_OLLAMA_MODEL`. Ollama must be installed and the chosen model pulled separately. Never print or commit `.env` values.

`run draft --input <draft.json> --output <new.md>` creates a local Markdown GitHub issue or email draft from an approved JSON input, previews the content, and requires approval bound to a new output path and SHA-256 digest. It never contacts GitHub or an email service. Issue JSON uses `kind`, `repository`, `title`, and `body`, with optional `sourceIssueUrl`; email JSON uses `kind`, `subject`, and `body`, with optional `to`. As with other Node path-based artifact output, it does not protect against a hostile concurrent swap of the approved output directory.

`run specialist-review --root <directory> --file <relative-path> [...]` locally reviews up to five approved source files, then asks separately before transfer. It runs up to two specialist prompts and a parent review on the selected provider with one shared 40-request/30-action budget. Workers can use only a literal search tool over the approved, heuristically redacted excerpts; the parent has no tools. No file, browser, shell, GitHub-write, messaging, nested delegation, persistence, or write access is provided. Findings are unverified and need human review.

The supported tool scope and phase states are tracked in `task.md`. `model-check` continues to use a fixed synthetic fixture; specialist review exposes only its approved-source literal search tool.

For local Ollama, set `TASKFORGE_PROVIDER=ollama`, `TASKFORGE_OLLAMA_MODEL`, and optionally `TASKFORGE_OLLAMA_CONTEXT_LENGTH` (default 4096; accepted range 1024–131072). The Ollama adapter uses native `/api/chat` requests to apply that context size. The default provider configuration remains Groq.

`run csv-analyze --input <path> [--numeric-column <header>]... [--output <new.json|new.csv|new.md>]` supports exact decimal totals for explicitly selected numeric columns. Structured exports contain row, duplicate-row, and missing-cell counts; if columns were selected, they also include those column labels and totals. Source cell values are never exported. The command previews the create-only report and confirms its exact path and SHA-256; the output folder needs persistent write approval. `run document-convert --input <path> --output <new.txt>` extracts bounded plain text from approved TXT, Markdown, text PDF, DOCX, or XLSX input. It previews the extracted text, requires a persistent write grant and exact path/hash confirmation, creates only a new file, and stores only the output metadata reference.

### Local schedules

Schedules are stored in the selected TaskForge database and run only while `schedule run` remains active in the foreground. Add a one-time UTC instant with `schedule add --workflow csv-analyze --input <path> --once 2035-01-01T00:00:00.000Z`, or a fixed interval with `--every-minutes <1..10080>`. `schedule list`, `pause <id>`, `resume <id>`, and `delete <id>` manage them (delete is a confirmed soft delete). Each due run asks for approval again and reacquires exact-file read approval. If no interactive user is present, it remains awaiting approval. The runner records missed runs and skips them. No Windows Task Scheduler job or background service is installed.
